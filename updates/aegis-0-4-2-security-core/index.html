Vom alten Heim-PC zum eigenen Security Core: JARVIS AEGIS 0.4.2

01 // AEGIS-0.4.2

Aus Security-Ideen wurde JARVIS AEGIS

Seit dem letzten öffentlichen Update vom 24. Juli entstand ein zusammenhängendes Sicherheitsdach für Zero Trust, sichere Softwarelieferung, Telemetrie, Event Evidence, Backup, Recovery, Sensoren und das eigene SOC. AEGIS bezeichnet das gesamte Sicherheitsprogramm; AEGIS SOC NEXUS ist die darin enthaltene read-only Operatoroberfläche.

02 // AEGIS-0.4.2

Der erste eigene JARVIS Core Node

Ein älterer Heim-PC wurde als erster privater JARVIS Core Node neu aufgebaut: minimales System ohne Desktop, UEFI mit LUKS/LVM, Key-only-Administration ohne Rootlogin, nftables Default-Deny, AppArmor und automatische Sicherheitsupdates. Es existiert keine Router-Portweiterleitung. Founder-Zugriff erfolgt ausschließlich über einen eng begrenzten Zero-Trust-Pfad.

03 // AEGIS-0.4.2

Reale Events statt erfundener Telemetrie

Der eigene append-only Eventstore nimmt ausschließlich sanitisierte, policygebundene Core- und Founder-Health-Ereignisse auf. Source, Schema, Größe, Zeit und Integritätskette werden geprüft; ein öffentlicher Datenbankport existiert nicht. Fehlende Quellen bleiben sichtbar N/A, NOT CONNECTED oder SOURCE GATED.

04 // AEGIS-0.4.2

Backup und Recovery praktisch bewiesen

Die Recoverykette besteht aus konsistentem SOC-Snapshot, age-verschlüsselter Ablage, externem Restore ausschließlich in tmpfs, erneuter SQLite- und Eventkettenprüfung, externem Ed25519-Checkpoint und einer physisch getrennten signierten Offlinekopie auf USB. Unmount, Remount und vollständiger Restore wurden real ausgeführt.

05 // AEGIS-0.4.2

Zwölf eigene Kontrollbereiche

AEGIS SOC NEXUS 0.4.2 besitzt Global Sentinel, Event Command Center, Asset Matrix, Incident Control, Identity Core, Exposure und Patch Control, Development Security, Network Defense, Vault und Key Control, Backup und Recovery Core, Sensor Fabric sowie Business Services. Die Workspaces sind real; noch nicht akzeptierte Backendquellen werden nicht simuliert.

06 // AEGIS-0.4.2

Erster signierter Browser-Updatepfad

Das echte Founder-Browserupdate von 0.4.1 auf 0.4.2 nutzte ein kanonisches Manifest, Ed25519-Signaturprüfung, exakte Basis- und Zielversion, Payload-Digest, 190 bestandene Tests, getrenntes Review und Arm, eine 60 Sekunden gültige Einmalfreigabe, transaktionalen Austausch und automatischen Rollback. Erst der Abschlussbeleg UPDATE_APPLIED / PASS schloss die Abnahme.

07 // AEGIS-0.4.2

Fehler sichtbar gehalten

Eine zu aggressive Härtung des einzigen Remote-Connectors unterbrach den Zugang zeitweise. Core und Daten blieben intakt; die akzeptierte Baseline wurde wiederhergestellt. Daraus gilt verbindlich: keine Änderung am einzigen Managementpfad ohne unabhängigen Rollback und zweiten Zugang. Auch Lifecycle-, Socket-, Dateisystem- und Versionsfehler des Updatepfads wurden nicht umetikettiert, sondern blockierten oder rollten zurück und erhielten Regressiontests.

08 // AEGIS-0.4.2

Nächste kontrollierte Gates

Als Nächstes werden weitere read-only Quellen einzeln und minimal berechtigt aufgenommen, Recovery-, Development- und Patch-Evidence produktiv gebunden, Identity- und Vulnerability- beziehungsweise SBOM-Quellen definiert sowie Incident Cases und Chain of Custody entwickelt. Weitere eigene Geräte und Dienste folgen als klar getrennte Collector. Aktive Reaktion bleibt einem späteren, autorisierten und auditierbaren Broker vorbehalten.

09 // AEGIS-0.4.2

Transparenzgrenze

AEGIS ist noch kein fertiges Enterprise-SOC, aber auch kein UI-Mock-up mehr. Core Node, Eventaufnahme, Restore, Offline-Recovery, Founder Access und signierter Updatepfad sind real belegt. Kritische Aktionen bleiben NOT ARMED. Unser Grundsatz: reale Quellen, sichtbare Grenzen, keine Fake-Telemetrie und Recovery vor kritischer Automation.

TRANSPARENCY // Dieser Bericht beschreibt den dokumentierten Projektstand am angegebenen Datum. Spätere Tests können den Status erweitern oder korrigieren.
